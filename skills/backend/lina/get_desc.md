Сгенерируй описание для Pull Request на основе текущего контекста сессии (диффа, обсуждения задачи, принятых решений).

## Формат

Строгая структура из трёх секций:

```markdown
## Что

Коротко, что именно добавлено/изменено/удалено. Основные эндпоинты, классы, фичи. Без пересказа диффа построчно — достаточно, чтобы ревьюер понял масштаб.

## Почему

**Главная секция.** Для каждого неочевидного решения — отдельный буллет:
- **<суть решения>** — почему выбран именно такой подход, что было альтернативой, какой trade-off. Без этого через месяц никто не вспомнит контекст.

Включать сюда:
- нестандартные архитектурные выборы
- отступления от паттерна соседей (и почему)
- зависимости/блокировки других задач
- компромиссы, которые ревьюер может заметить и захотеть обсудить
- workaround'ы и их причины

НЕ включать сюда:
- тривиальные «добавил класс Х, добавил метод Y» — это в «Что»
- пересказ диффа

## Тесты

Коротко: что тестируется и сколько тест-кейсов в каждом файле. Если какой-то аспект осознанно НЕ покрыт — упомянуть почему.
```

Затем — отдельный блок для тестировщика, после `---` (чтобы его удобно было скопировать отдельно от PR-описания):

```markdown
---

## Для тестировщика

### Эндпойнты

Список затронутых эндпойнтов с краткой подписью «что делает / что принимает / что возвращает». Пропустить секцию, если PR не трогает публичное API.

### Базовый сценарий

2–5 шагов в стиле «дёрнуть X → получить Y → дёрнуть Z». Без дублирования с «Эндпойнтами» — здесь важна последовательность.

### Что проверить

Конкретные edge cases. Один кейс — одна строка, по возможности с ожидаемым кодом/сообщением. Auth, валидация форматов/типов, граничные значения, негативные сценарии, варианты входных данных, которые отличаются от happy path.

### Куда смотреть

Где искать диагностику: путь к логам, Redis-ключи, основной файл-имплементация. Что-то одно или несколько — что реально полезно тестировщику для проверки причины бага, если он найдётся.

### Ограничения

Что осознанно НЕ покрыто этим PR и где это будет — ссылка на следующую задачу, если есть. Известные временные заглушки.
```

Если PR меняет контракт API (поля запроса/ответа, эндпоинты, дефолтное поведение, коды ошибок) — после блока тестировщика добавить ещё один блок, тоже отделённый `---` (по нему фронтам заводят задачи):

```markdown
---

## Для фронта

Список изменений контракта, по одному буллету на изменение: что удалено/добавлено/изменено и что фронту с этим делать (какой параметр передавать, какое поле больше не приходит, какую новую ошибку обрабатывать). Только фактические изменения контракта — внутренние рефакторы сюда не писать. Если контракт не менялся — блок пропустить целиком.
```

Последним — блок для аналитика, тоже после `---`. Он нужен, если реализация в чём-то разошлась
с тех-доком или спецификацией в вики, либо если изменения контракта затрагивают задачи фронта.
Если расхождений нет и задачи фронта всё покрывают — блок пропустить целиком.

Перед тем как его писать, обязательно:

1. **Перечитать источники** — тех-док задачи и страницу в вики (MCP `yandex-wiki`, плюс волт
   `/Users/zhukov/Obsidian/obsid/raw/` и `wiki/`), сверить с фактическим поведением кода.
2. **Проверить задачи фронта в Трекере** (`issues_find` по `[Front]` и теме задачи) — покрывают ли
   они изменения контракта и не описан ли там старый вариант. Явно сказать, нужна ли новая задача
   или достаточно уточнения в существующей (с её ключом).

```markdown
---

## Для аналитика

Список расхождений с документацией, по одному буллету на расхождение: что написано в доке, что
сделано в коде, почему. Отдельно помечать те, что появились по решению ревьюера или продакта, —
их надо занести в документ, иначе смежные задачи сделают по старому описанию.

Ниже отдельными абзацами, если есть:
- дыры в цепочке задач, обнаруженные по пути (что-то не покроет ни одна из запланированных задач);
- пункты доки, помеченные как несогласованные, по которым согласования так и не видно.

Вывод по задачам фронта: какие ключи покрывают изменения контракта, где нужно уточнение, нужна ли
новая задача.
```

## Правила

- На русском.
- Без эмодзи.
- Без «🤖 Generated with Claude».
- Ссылки на задачу в трекере / связанные PR — не вставлять, пользователь сам добавит при необходимости.
- Если по ходу реализации находились ошибки/расхождения в спеке — упомянуть их отдельным пунктом в «Почему» («почему отступили от буквы спека»).
- Если какое-то решение из «Почему» уже обсуждалось с пользователем в сессии — формулировка должна отражать реальную мотивацию из обсуждения, а не выдумываться.
- В блоке «Для тестировщика» подсекции пропускать, если нерелевантны (нет публичного API → нет «Эндпойнтов»; нет внешних зависимостей → нет «Куда смотреть»). Содержимое — конкретика, не пересказ «Что/Почему» — тестировщик читает блок отдельно.

## Краткость основного описания (ВАЖНО)

Основная часть (всё до `---`) должна быть **короткой**: обычно 20–35 строк суммарно, редко больше. Лучше пожертвовать деталями, чем растечься.

- **«Что»** — только функциональные дельты эндпоинтов/моделей/контрактов/новых классов и сервисов, важных ревьюеру. Косметику (переименования переменных и helper-классов, перенос строк, мелкие рефакторы внутри функции) **не упоминать вовсе** — это видно по диффу.
- **«Почему»** — максимум 5–7 буллетов, каждый в 1–2 предложения. Включать только решения, которых ревьюер не выведет из кода. Не дублировать «Что». Тривиальные выборы не объяснять.
- **«Тесты»** — 1–3 строки. Имя/количество кейсов кратко; построчное перечисление не нужно.

Блоки «Для тестировщика» и «Для аналитика» эти ограничения **не касаются** — их подробность регулируется только своими правилами выше; не урезай их ради краткости основной части.

## Вывод

Просто markdown-текст описания в чат — без кодовых блоков вокруг всего описания, без преамбулы «вот твоё описание». Каждый блок для смежников — «Для тестировщика», «Для фронта», «Для аналитика» — отделить строкой `---`, чтобы их можно было скопировать по отдельности.
