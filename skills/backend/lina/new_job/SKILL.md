# Выполнение backend-задачи New_job (очередь MCA)

Воркфлоу для задач в `~/Projects/New_job/backend`. Строго по этапам, с
остановками на согласие. Не перепрыгивать вперёд: план — отдельный шаг, тесты —
в самом конце, после проверки кода.

Аргумент скилла — номер задачи (например `696`); ключ собирается как
`MCA-<номер>`. Если Лина всё же передала полный ключ `MCA-696` — принять как
есть. Если номер не передан — спросить.

## Базовые правила (действуют на всех этапах)

- Отвечать по-русски, без эмодзи, коротко и по делу, простым языком.
- **Перед правкой файлов — показать план и дождаться явного согласия.** Не
  начинать код без «go».
- **Спрашивать перед поиском по проекту** (grep/find по backend), объясняя зачем.
- На любой развилке (два толкования, выбор подхода) — явно уточнять у Лины,
  не решать молча. Вопрос задавать развёрнуто: сначала контекст и зачем
  спрашиваю, потом варианты.
- **Тесты не запускать и не коммитить самому** — давать готовую команду. Пушить
  самому нельзя. Исключение — если Лина явно попросит «запусти»/«закоммить».
- Коммиты однострочные, без футера `Co-Authored-By`.

## Этап 1. Разбор задачи

1. Загрузить задачу из трекера: `mcp__yandex-tracker__issue_get` (с описанием) +
   `issue_get_comments`. Взять из ответа: описание, чек-лист (критерии готово),
   `parent` (родитель-эпик), story points.
2. **Прочитать контекст вокруг:**
   - Родительскую задачу (`parent.key`) — понять место задачи в эпике.
   - Соседние задачи эпика (`issues_find` по родителю или связям) — чтобы знать,
     что делают смежные таски и где границы текущей (частая ловушка: часть
     упомянутого в тех-доке — уже другая задача).
   - Вложения задачи, если есть (`issue_get_attachments`) — скриншоты, PDF.
   - Тех-док: вызвать агента `wiki-research` с ключом задачи и ссылкой на вики,
     если она есть в описании. Самому по вики не искать.
3. Изложить Лине разбор простым языком: что меняем, объём, критерии готово,
   и главное — **что в задачу НЕ входит** (границы). Снять неоднозначности
   через источник (описание/тех-док), а не гадать.
4. На чтение кода в `~/Projects/New_job/backend` — спросить разрешение
   (перечислить конкретные файлы и зачем).

## Этап 2. План (отдельный шаг)

- Прочитать релевантный код (после разрешения).
- Составить пофайловый план: что и где меняем, какие открытые вопросы/развилки.
- Показать план и открытые вопросы. **Дождаться явного «go».**
- После одобрения — сначала кратко пересказать итог/договорённости и ещё раз
  дождаться «go», только потом править файлы.

## Этап 3. Выполнить задачу (код)

- Хирургические правки: трогать только то, что связано с задачей, без попутного
  рефакторинга. Стиль — как у соседнего кода.
- Держать код-стиль проекта: строка ≤119 символов, именованные аргументы при
  вызове, полные имена переменных, docstring одной строкой, без ссылок на MCA в
  коде, без реэкспортов в `__init__.py`.
- Правки оставлять в рабочем дереве. Не коммитить.

## Этап 4. Проверить сделанное

- Убедиться, что изменения покрывают все пункты чек-листа задачи.
- Грепом проверить, что не осталось старых имён/параметров и нет случайных
  задетых мест (например, одноимённые методы в других модулях — не наши).
- Если ветку обновляли поверх base — проверить отсутствие merge-конфликтов
  (`grep '^<<<<<<<'`), при разрешении: имена/контракт из текущей задачи, логику
  под актуальную модель из base.
- Доложить итог по файлам. Это ещё НЕ тесты.

## Этап 4.5. Сверка с документацией и контрактом фронта

Делать после проверки кода, до тестов.

1. **Сверить поведение с документацией Даши в вики.** Спросить агента
   `wiki-research`, что решено по теме задачи, и сравнить его ответ с кодом.
   Если фактическое поведение кода расходится с описанным в документации —
   **сначала сообщить Лине**, простым человеческим языком, как ребёнку: что
   написано в доке, что делает код, чем это грозит. Не молчать и не решать
   молча, что «дока устарела».
2. **Проверить, поменялся ли контракт для фронта** — тело/поля ответа, коды
   статусов, параметры запроса, состав и смысл возвращаемых данных.
   Если поменялся:
   - посмотреть в Трекере, есть ли на это задача (`issues_find`);
   - если задачи нет — сформулировать сообщение для продакта: без терминов,
     без имён полей и кода, на языке «что увидит пользователь и что нужно
     сделать фронту». Показать Лине черновик, не отправлять самому.

## Этап 5. Тесты (в самом конце)

- Тесты писать после проверки кода, не раньше.
- Тестировать фичу через HTTP-эндпоинт (`make_get`/`make_post` и т.п.), не через
  ORM (`aget`/`acount`).
- Данные — только через фикстуры (`tests/fixtures/<app>.py`), не ORM-вызовы в
  `async def`. Мержить `defaults | (data or {})`.
- Конвенции: один аспект — один файл `test_<resource>_<аспект>.py`, docstring
  одной строкой, минимум ассертов (`count` достаточно), `params`/`data` — в
  переменную строкой выше, `make_get` в одну строку.
- Access-тесты: порядок 200 → 401 → 403; доступы тестировать от скоупов
  (ALL/TEAM/OWN), не от конкретных ролей.
- **Не** писать тесты на выпиленное (404/405, «поля больше нет», «старый
  параметр игнорируется») — по правилу «не тестируем удалённое».
- Дать команду на прогон:
  `docker compose exec app_metrica pytest tests/<путь> -v`
