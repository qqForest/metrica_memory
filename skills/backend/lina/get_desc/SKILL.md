Сгенерируй описание для Pull Request на основе текущего контекста сессии (диффа, обсуждения задачи, принятых решений).

## Формат

Строгая структура из трёх секций:

```markdown
[MCA-XXXX](https://tracker.yandex.ru/MCA-XXXX)

## Что

Коротко, что именно добавлено/изменено/удалено. Основные эндпоинты, классы, фичи. Без пересказа диффа построчно — достаточно, чтобы ревьюер понял масштаб.

## Почему

**Главная секция.** Для каждого неочевидного решения — отдельный буллет:
- **<суть решения>** — почему выбран именно такой подход, что было альтернативой, какой trade-off. Без этого через месяц никто не вспомнит контекст.

Включать сюда:
- нестандартные архитектурные выборы
- отступления от паттерна соседей (и почему)
- зависимости/блокировки других задач
- компромиссы, которые ревьюер может заметить и захотеть обсудить
- workaround'ы и их причины

НЕ включать сюда:
- тривиальные «добавил класс Х, добавил метод Y» — это в «Что»
- пересказ диффа

## Тесты

Коротко: что тестируется и в каких файлах. Число кейсов и итоги прогона («N passed») не писать. Если какой-то аспект осознанно НЕ покрыт — упомянуть почему.
```

Блоки для смежников (тестировщик, фронт, аналитик) генерировать всегда, кроме PR в ветку `development-permissions` — её фронт и тестировщик не видят.

Затем — отдельный блок для тестировщика, после `---` (чтобы его удобно было скопировать отдельно от PR-описания):

```markdown
---

## Для тестировщика

### Эндпойнты

Список затронутых эндпойнтов с краткой подписью «что делает / что принимает / что возвращает». Пропустить секцию, если PR не трогает публичное API.

### Базовый сценарий

2–5 шагов в стиле «дёрнуть X → получить Y → дёрнуть Z». Без дублирования с «Эндпойнтами» — здесь важна последовательность.

### Что проверить

Конкретные edge cases. Один кейс — одна строка, по возможности с ожидаемым кодом/сообщением. Auth, валидация форматов/типов, граничные значения, негативные сценарии, варианты входных данных, которые отличаются от happy path.

### Куда смотреть

Где искать диагностику: путь к логам, Redis-ключи, основной файл-имплементация. Что-то одно или несколько — что реально полезно тестировщику для проверки причины бага, если он найдётся.

### Ограничения

Что осознанно НЕ покрыто этим PR и где это будет — ссылка на следующую задачу, если есть. Известные временные заглушки.
```

Если PR меняет контракт API (поля запроса/ответа, эндпоинты, дефолтное поведение, коды ошибок) — после блока тестировщика добавить ещё один блок, тоже отделённый `---` (по нему фронтам заводят задачи):

```markdown
---

## Для фронта

Первой строкой — нужна ли фронту задача: «Задачи на это нет, нужно завести» или «Новых задач не требуется». Одна фраза, без разбора чужих задач и их содержимого.

Список изменений контракта, по одному буллету на изменение: что удалено/добавлено/изменено и что фронту с этим делать (какой параметр передавать, какое поле больше не приходит, какую новую ошибку обрабатывать). Только фактические изменения контракта — внутренние рефакторы сюда не писать. Если контракт не менялся — блок пропустить целиком.
```

Последним — блок для аналитика, тоже после `---`. Он нужен, если реализация разошлась с тех-доком
или спецификацией в вики. Если расхождений нет — блок пропустить целиком.

Сверять только со свежей тех-спекой аналитика в вики (MCP `yandex-wiki`, раздел `razrabotka-produkta/moduli/...`).
Если у аналитика страницы по теме задачи ещё нет — блок пропустить целиком. Старые спеки
(`metrica/product/specs/...`) не смотреть: они удаляются, расхождения с ними аналитику не нужны. Перед тем как
писать блок, перечитать спеку и сверить с фактическим поведением кода.

```markdown
---

## Для аналитика

Список расхождений с документацией, по одному буллету на расхождение: раздел доки и цитата, как на
деле, готовый текст правки. 3-4 предложения бытовым языком — без имён классов, кодов ошибок,
`permission`; номера требований (ПРВ-08) оставлять. Почему бэкенд сделал так — не объяснять.
Отдельно помечать те, что появились по решению ревьюера или продакта, — их надо занести в документ,
иначе смежные задачи сделают по старому описанию. Баги, найденные по пути, сюда не писать.

Только то, что касается текущей задачи. Чужие задачи, их содержимое и состояние — не разбирать.
Ниже отдельным абзацем, если есть: пункты доки, помеченные как несогласованные, по которым
согласования так и не видно.
```

## Правила

- На русском.
- Без эмодзи.
- Без «🤖 Generated with Claude».
- Первой строкой — ссылка на задачу: `[MCA-XXXX](https://tracker.yandex.ru/MCA-XXXX)`, несколько задач — через ` · `. То же в комментарии к PR в GitHub. Ссылки на связанные PR не вставлять.
- Если по ходу реализации находились ошибки/расхождения в спеке — упомянуть их отдельным пунктом в «Почему» («почему отступили от буквы спека»).
- Если какое-то решение из «Почему» уже обсуждалось с пользователем в сессии — формулировка должна отражать реальную мотивацию из обсуждения, а не выдумываться.
- **Никакой истории правок.** Описывать только текущее состояние и его причины. Не писать «по правке ревью», «убрано по замечанию», «сначала было так, потом переделали», «изначально делали иначе». Переписка ревью уже лежит в комментариях PR, а прежние редакции — в истории коммитов; в описании это шум.
- **Не писать о том, чего не делали** — «не стали трогать», «решили не добавлять», «альтернативу отбросили». Исключение ровно два: секция «Тесты» (осознанно непокрытый аспект) и подсекция «Ограничения» для тестировщика.
- **Никаких надуманных альтернатив.** Формат «выбрали X, а не Y» допустим, только если Y реально существовал: был в постановке, в тех-доке, в комментарии ревьюера или обсуждался с пользователем. Вариант, который придумал сам и сам же отверг, в описание не попадает — вместо «сделали X, а не Y» пишется просто «сделали X, потому что <причина>».
- **Никаких имён коллег.** Автор решения обозначается ролью: «решение ревьюера», «решение продакта», «решение аналитика».
- **Только то, что относится к этой задаче.** Находки про соседние и будущие задачи, дыры в их покрытии и чужие сроки в описание не попадают — ни в один блок.
- **Не утверждать того, в чём не уверен.** Если расхождение документов не проверено до конца или на код не влияет — не выносить его вовсе.
- В блоке «Для тестировщика» подсекции пропускать, если нерелевантны (нет публичного API → нет «Эндпойнтов»; нет внешних зависимостей → нет «Куда смотреть»). Содержимое — конкретика, не пересказ «Что/Почему» — тестировщик читает блок отдельно.

## Краткость основного описания (ВАЖНО)

Основная часть (всё до `---`) должна быть **короткой**: обычно 20–35 строк суммарно, редко больше. Лучше пожертвовать деталями, чем растечься.

- **«Что»** — только функциональные дельты эндпоинтов/моделей/контрактов/новых классов и сервисов, важных ревьюеру. Косметику (переименования переменных и helper-классов, перенос строк, мелкие рефакторы внутри функции) **не упоминать вовсе** — это видно по диффу.
- **«Почему»** — максимум 5–7 буллетов, каждый в 1–2 предложения. Включать только решения, которых ревьюер не выведет из кода. Не дублировать «Что». Тривиальные выборы не объяснять.
- **«Тесты»** — 1–3 строки. Имя/количество кейсов кратко; построчное перечисление не нужно.

Блоки «Для тестировщика» и «Для аналитика» эти ограничения **не касаются** — их подробность регулируется только своими правилами выше; не урезай их ради краткости основной части.

## Публикация

Описание только показать в чате. Публиковать по отдельной явной команде, после правок текста — снова ждать её.

- «Что / Почему / Тесты» — в описание PR в GitHub.
- Блоки для смежников — в задачу Трекера, каждый блок отдельным комментарием: смежники в GitHub не заходят.
- Один PR на две задачи — сначала прочитать комментарии обеих, там может стоять указатель «обсуждение в
  MCA-XXX». Указателя нет — спросить, куда класть.
- Контракт уточнился после отправки блока — писать новый комментарий, старый не править.
- `summonees` — по правилу `tracker.md`.

## Вывод

Просто markdown-текст описания в чат — без кодовых блоков вокруг всего описания, без преамбулы «вот твоё описание». Каждый блок для смежников — «Для тестировщика», «Для фронта», «Для аналитика» — отделить строкой `---`, чтобы их можно было скопировать по отдельности.
