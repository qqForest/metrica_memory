# Оценка задач MCA в story points

Оценивать задачи в **story points по шкале команды**, а не в днях «от себя».
Шкала у команды компактная: больше всего задач на 1 SP, типовая фича — 2,
3 — потолок. Прежде чем называть цифру — свериться с калибром ниже и с тем,
как оценены соседние задачи.

## Калибр команды (сверено по ~200 задачам `[Back]`, 15.10.2026)

| SP | Что это | Эталоны |
|---|---|---|
| 1 | Точечная правка: одно поле или фильтр, правка схемы, баг с понятной причиной, права роли data-миграцией, обязательное поле с миграцией | 1009 плановые границы в списке смен, 1181 фильтр публикации, 892/880 правки схемы, 865 смена пароля и сессия, 1179 права роли Пользователь, 1183 tenant_id обязателен, 1327 запрет отметок на черновик |
| 2 | Новая логика в одном месте: правило видимости, проверка при создании, фильтр с подзапросом, набор связанных полей | 1180 отметка/заработок/ставка в своих сменах, 1155 проверка локации при постановке смены, 1263 права отсутствий, 567 вход по email/логину |
| 3 | CRUD с нуля, объединение эндпоинтов, новый механизм, сложная валидация при записи | 1363 CRUD целей, 907/909 объединение смен, 906 пересечение смены и отсутствия, 764 обработка заявок с уведомлениями |
| 5 | Только инфраструктура и архитектура, у фич не бывает | 1161, 1236, 901 |

Если механизм уже есть в коде и задача его расширяет — это на ступень ниже
задачи, которая его строила (764 = 3 → расширение автоотклонения = 1).

Аргумент скилла — номера задач: одна (`736`), список (`736,738`) или диапазон
(`736-739`). Ключи собираются как `MCA-<номер>`. Если не передано — спросить.

## Что делать

1. **Собрать оцениваемые задачи и их контекст.** Через
   `mcp__yandex-tracker__issue_get` прочитать описание и чеклист каждой
   задачи. Через `issue_get_links` на родителе (эпике) — найти все
   соседние подзадачи.

2. **Вытянуть шкалу команды.** Одним `issues_find` по ключам соседей запросить
   поля `["key","summary","status","storyPoints"]`. Смотреть на `storyPoints`
   уже оценённых соседей и сверять с калибром выше. Если соседей мало — общий
   запрос: `Queue: MCA "Story Points": notEmpty() Components: "Бэкенд"
   Summary: "[Back]" "Sort By": Updated DESC` (в YQL поле пишется
   `"Story Points"`, фильтр `storyPoints` даёт 422).

3. **Пройтись по коду** задачи в `~/Projects/New_job/backend` (модели, вью,
   сериализаторы, фильтры, миграции): подтвердить, что описание бьётся с кодом,
   и найти скрытый объём — кросс-доменные вызовы, влияние на тесты других
   приложений, миграции. Спросить перед поиском по проекту, если Лина этого
   ещё не разрешила в текущей сессии.

4. **Оценить в SP относительно соседей**, а не в днях. По каждой задаче явно
   назвать ближайший аналог из калибра («как 1009 = 1»). Если задача выходит за потолок
   шкалы (>3) — это сигнал **дробить**, предложить разрез на подзадачи по 2-3 SP.

5. **Ответ:** таблица соседей с их SP → цифра по каждой оцениваемой задаче →
   риски/скрытый объём → где есть миграции. Коротко, простым языком.

## Не делать

- Не называть оценку в днях как основную (можно как справку, но шкала — SP).
- Не выдумывать SP, не сверившись с соседями.
- Не ставить 2 «по умолчанию»: точечная правка — это 1, так оценена большая часть задач.
- Не завышать: даже самая мясная типовая задача у команды укладывается в ~3 SP;
  большая цифра = повод дробить, а не героически брать целиком.
