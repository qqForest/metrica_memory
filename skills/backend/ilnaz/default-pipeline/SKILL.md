description: Дефолтный пайплайн перед стартом задачи Metrica — собрать контекст из Трекера, кода, соседних PR и metrica_memory, сформулировать вопросы и согласовать скоуп. Код не пишем, только разведка.
---

Когда пользователь вызывает `/default-pipeline`, начни сбор контекста по задаче перед написанием кода.

## Аргументы

- `$ARGUMENTS` — ключ задачи (`MCA-XX` или просто число; для числа подставь префикс `MCA-`). Если не указан — спроси у пользователя.

## Главные принципы

- **Код не пишем** на этом этапе. Цель — понять задачу, скоуп, паттерны проекта, и согласовать допущения.
- **Не дублируем работу субагентов** — если делегируешь поиск Agent-у, сам параллельно те же файлы не читаешь.
- **Параллелизм везде, где можно** — несколько `issue_get`, `Read`, `Bash` в одном сообщении.
- **Не делай молчаливых допущений** — каждое допущение выноси в финальный список как «дефолт, если не возразят».

## Воркфлоу

### Шаг 1 — Прочитать саму задачу

Параллельно:

1. `mcp__yandex-tracker__issue_get` с `issue_id=<KEY>`, `include_description=true`.
2. `mcp__yandex-tracker__issue_get_comments` — комментарии (часто содержат уточнения от ревьюера/PM).
3. `mcp__yandex-tracker__issue_get_url` — ссылка на задачу для финального дайджеста.
4. `mcp__yandex-tracker__issue_get_links` — связи (parent, blockers, related).

Из ответа зафиксируй: **summary**, **описание**, **status**, **assignee**, **parent**, **sprint**, **story points**, **components**, **теги**.

### Шаг 2 — Прочитать родительскую задачу и связанные

Если есть `parent` — обязательно вызови `issue_get` + `issue_get_comments` + `issue_get_links` на родителя. Родитель обычно содержит:

- User Story (как менеджер хочу...)
- Контекст и зачем
- Чеклист приёмки (`checklistItems`) — часто отвечает на вопросы скоупа
- Перечень дочерних задач (через `issue_get_links`) — карта стори

Из `issue_get_links` родителя достань ключи всех дочерних задач: `[Front]`/`[Back]` задачи, фронтовые часто описывают пользовательский сценарий точнее, чем бэковые.

### Шаг 3 — Найти соседние задачи спринта

```
mcp__yandex-tracker__issues_find
  query: Queue: MCA AND Sprint: "<имя спринта>" AND Components: "Бэкенд" "Sort By": Updated DESC
  fields: ["key","summary","status","assignee","parent","story_points","tags","updated_at"]
  include_description: false
  per_page: 100
```

Это даёт:

- Карту всех бэк-задач спринта со статусами (что уже готово, что в работе, что в очереди).
- Кто что делает — соседи по стори.
- Образцы стиля от **тех же исполнителей** в этом же спринте (особенно ценно для шаблонов CRUD-задач).

Из списка выбери **3–5 наиболее релевантных**:

- Все задачи под тем же `parent` (соседи по стори).
- Задачи **того же типа** (CRUD/парсер/настройки), уже выполненные в спринте — это эталон стиля для текущей.
- Задачи, от которых наша **зависит** (создают модели/эндпоинты, которые мы используем).

### Шаг 4 — Прочитать детали ключевых соседних задач

Для выбранных в шаге 3 — параллельно:

1. `issue_get` с описанием для каждой.
2. `issue_get_comments` — там часто лежит:
   - финальный «отчёт для QA» автора (формат «## Что / ## Доступ / ## Эндпоинты / ## Бизнес-правила / ## Чек-лист»);
   - ссылки на PR (`https://github.com/metrica-erp/backend/pull/XXX`);
   - уточнения от ревьюера.

### Шаг 5 — Прочитать PR-ы соседних задач

Из комментариев шага 4 вытащи номера PR, потом для каждого параллельно:

```bash
gh pr view <NUM> --json title,body,state,files,labels
```

PR body содержит «## Что сделано» — образец того, как формулируется выполненная работа. `files` показывают **структуру файлов** для типового изменения (миграции, views, serializers, services, tests, fixtures). Это шаблон, на который опираемся.

При необходимости — `gh pr diff <NUM> --name-only` для полного списка файлов.

### Шаг 6 — Прочитать текущий код по теме

Параллельно:

1. `grep -rln "<MainEntityName>" --include="*.py"` — найти, где упоминается основная сущность задачи.
2. `Read` на найденные ключевые файлы:
   - `<app>/models.py` — текущая структура модели (какие поля уже есть, что наследуется).
   - `<app>/views.py` (или `views/`) — есть ли уже ViewSet, какие эндпоинты.
   - `<app>/serializers.py` (или `serializers/`).
   - `<app>/urls.py`.
   - `<app>/services/`.
   - `<app>/apps.py`.
   - `<app>/choices.py`, `<app>/exceptions.py` — если есть.
3. `ls <app>/` + `ls <app>/migrations/` — общая структура.
4. `Read` последней миграции — состояние схемы в БД.

Если нужны паттерны от соседних модулей (soft-delete, audit-log, scope) — `grep` по `deleted_at`, `*Log`, `ScopedViewSetMixin` в `shifts/`, `references/`, `user_profiles/` и прочитай 1–2 канонических образца.

### Шаг 7 — Прочитать metrica_memory правила (**строго, не по памяти**)

**Главное правило шага:** правила читаются **через `Read` целиком**, каждый применимый файл — открой и прочитай от начала до конца. Не полагайся на то, что «помнишь это правило» — выполнение задачи без актуального текста правил перед глазами регулярно приводит к пропущенным пунктам (порядок тестов, URL-стиль, single-source паттерны). Перечитай весь применимый набор **в этой же сессии**, даже если делал похожую задачу неделю назад.

Параллельно. Базовые — всегда:

- `/Users/forestmac/Projects/metrica_memory/rules/karpathy.md` — четыре принципа.
- `/Users/forestmac/Projects/metrica_memory/rules/shared/ru-language.md`.

Для backend-кода — всегда:

- `/Users/forestmac/Projects/metrica_memory/rules/shared/backend-style.md`.

Дополнительно — по характеру задачи. Выбирай только релевантные, но **прочитай выбранные целиком**:

| Когда | Файл |
|---|---|
| ViewSet/CRUD | `rules/shared/viewset-patterns.md` |
| Serializers | `rules/shared/serializer-patterns.md` |
| Сервисный слой / транзакции | `rules/shared/service-layer.md` |
| Бизнес-валидации (raise 400 из ViewSet/Serializer) | `rules/shared/custom-exceptions.md` |
| Soft-delete (`deleted_at`) | `rules/shared/soft-delete.md` |
| Audit-логирование (`*Log` модели) | `rules/shared/audit-logging.md` |
| Миграции (особенно data-миграции) | `rules/shared/django-migration-pitfalls.md` |
| Тесты CRUD | `rules/shared/test-patterns-crud.md` |
| Тесты list/фильтры | `rules/shared/test-patterns-list-filters.md` |
| `sync_to_async` в тестах | `rules/shared/tests-sync-to-async.md` |

Не читай весь набор — только то, что задача затрагивает. Если в задаче нет CRUD — не нужны `viewset-patterns`. Но всё, что выбрал — открой и прочитай полностью.

Параллельно перечитай **все актуальные `feedback_*.md` из user-memory** в этой сессии: это live-фидбэк, который обновляется чаще shared-правил и часто содержит конкретные грабли последних задач. Список — в `MEMORY.md`; читать целиком все `feedback_*.md`, не по описанию из индекса.

**Чек перед выходом из шага:** в финальном дайджесте (Шаг 9) явно перечисли, какие правила/feedback-файлы прочитаны в этой сессии, и какие именно их пункты влияют на скоуп. Если в задаче что-то идёт против правила — это отдельный открытый вопрос для пользователя.

### Шаг 8 — Фоллбэк: Obsidian-вики (опционально)

Если в `rules/shared/` и в коде ответа на вопрос нет — иди в Obsidian:

1. Сначала `Read` каталога: `/Users/forestmac/OBSIDIAN Work/wiki-llm-metrica/index.md`.
2. Из каталога — нужный путь:
   - `entities/scope-system.md`, `entities/<name>.md` — карточки сущностей.
   - `wiki/<topic>.md` — саммари модулей, ADR, тех-долг.
   - `raw/<date>_<topic>.md` — сырые дневники (только если в `wiki/` нет ответа).
3. Если и в вики нет — **спроси пользователя**, не угадывай.

### Шаг 9 — Финальный дайджест в чат

Сведи всё в структурированный пост для пользователя:

```markdown
## <KEY> — что увидел в таске + коде

**Что есть сейчас (<app>/):**
- Краткое состояние модели/views/serializers/тестов.
- Какие паттерны уже отлажены в соседних модулях (имена файлов с строками).

**Родительская стори <PARENT-KEY> (важно для скоупа):**
- User Story + ключевые пункты чеклиста.

## Что меня смущает в формулировке задачи

### N. <Конкретный вопрос или противоречие>
- Цитата из задачи / из стори, которая порождает вопрос.
- Мой разбор и предположение по умолчанию.

(Несколько таких блоков — по числу неясных моментов.)

## Подтверждённый скоуп задачи (по дефолту)

**Модель:** ...
**ViewSet:** ...
**Сериализаторы:** ...
**Сервис:** ...
**Валидации:** ...
**RBAC / scope:** ...
**Тесты:** структура файлов, бизнес-кейсы поверх матрицы 200/401/403/404.

## Сравнение скоупа с story points
Сколько SP заявлено vs сколько похожие соседние задачи стоили (ссылки на ключи). Реалистично / запросить переоценку.

## Открытые вопросы перед стартом

1. ...
2. ...

[<KEY>](https://tracker.yandex.ru/<KEY>) · статус: «...» · спринт: ... · SP: ...
```

### Шаг 10 — Согласовать и ждать команды

После дайджеста — **остановись и жди**. Не начинай писать код, пока пользователь не подтвердит скоуп или не ответит на открытые вопросы.

## Что НЕ делает этот скилл

- Не пишет миграции, модели, views, тесты — это уже фаза реализации.
- Не создаёт ветки и PR (это `/pr-metrica`).
- Не переводит задачу в «В работе» в Трекере (это `/task-update`).
- Не коммитит ничего (это `/commit`).

## Связанное

- `/task` — быстрая выжимка по задаче (без полного пайплайна).
- `/task-update` — смена статуса/исполнителя/ревьюера в Трекере.
- `/pr-metrica` — сдача задачи на ревью.
