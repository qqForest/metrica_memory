# Git workflow — Metrica

**Когда применять:** при создании веток, PR, ревью, мерджа любых изменений в репозитории Metrica (`metrica-erp`, `metrica-front`).

---

## Ветки

**Правило:** все ветки — от `development`. Hotfix — от `main-new` (прод).

| Тип | Шаблон | Пример |
|---|---|---|
| Фича | `feature/MCA-XX` | `feature/MCA-1452` |
| Баг | `bugfix/MCA-XX` | `bugfix/MCA-1190` |
| Хотфикс | `hotfix/MCA-XX` (от `main-new`) | `hotfix/MCA-99` |
| Техдолг | `chore/MCA-XX` | `chore/MCA-30` |

Несколько задач в одной ветке — номера через дефис: `feature/MCA-1279-1280`.

---

## Draft PR — сразу после первого коммита

**Правило:** Pull Request создаётся **в статусе Draft** сразу после первого коммита. Draft = «я работаю, можно посмотреть прогресс». Кнопка Merge заблокирована.

---

## Лейблы — обязательны

Каждый PR получает **две категории** лейблов: тип + прогресс.

**Тип:**

| Лейбл | Описание |
|---|---|
| `feature` | Новая функциональность |
| `bug` | Исправление ошибки |
| `tech debt` | Рефакторинг, оптимизация |
| `hotfix` | Срочное исправление |
| `docs` | Документация |

**Прогресс:**

| Лейбл | Описание |
|---|---|
| `dev` | В процессе (ставится при создании Draft PR) |
| `Dev.done` | Готово к ревью (заменяет `dev` при Ready for Review) |
| `urgent` | Нужен быстрый ревью |

**Пример переходов:** фича в работе → `feature` + `dev`. Завершена → `dev` меняется на `Dev.done`.

---

## Squash & Merge — единственный тип мерджа

**Правило:**
- **Squash & Merge** — единственный разрешённый тип мерджа.
- **Автор не мержит свой PR** — только ревьюер после Approve.
- Новые коммиты после Approve **сбрасывают** одобрение.
- Замечания — через **Request changes** с конкретными предложениями (Suggest changes).
- Не согласен с замечанием — обсуждай в треде, **не игнорируй**.
- Перед ревью — проверить существующие комментарии других ревьюеров и fix-коммиты автора, чтобы **не дублировать** замечания.

---

## Уведомления

**Правило:** при переводе задачи в «Ревью» — пост в топик **«Ревью»** группы «Платформа» в Telegram по шаблону:

```
https://tracker.yandex.ru/MCA-XX
PR: https://github.com/metrica-erp/<repo>/pull/XX
Ревьюер: @тег
Комментарий: -
```

После мержа, если нужно тестирование — в тот же топик с шаблоном тестировщика.

После исправления замечаний — ответ в том же треде: «Исправлено, готово».

---

## Сквозные задачи (front + back)

**Правило:** если выяснилось, что задача требует доработки другого стека:

1. Создать **подзадачу** на второй стек (даже если работы на 15 минут).
2. Добавить тег второго стека к родительской задаче.
3. Родительская задача **не переходит** в «Можно тестировать», пока подзадача не закрыта.
4. Последний разработчик (кто закрыл подзадачу) переводит родительскую задачу на тест.

Правило «30 минут» **не применяется** к межстековым зависимостям: задание в комментарии теряется.

---

## Hotfix flow

**Правило:**
1. Ветка от `main-new` (не от `development`).
2. PR в `main-new`.
3. Один Approve достаточно.
4. Лейблы `hotfix` + `urgent`.
5. После мержа — **cherry-pick** в `development`.

---

## Story Points — не меняются после старта

**Правило:**
- SP ставятся **до взятия в работу** — на груминге или планировании.
- Оценка **командная** — минимум 2 человека из подкоманды.
- Шкала Фибоначчи: 1, 2, 3, 5, 8, 13.
- После старта работы SP **не меняются**. Если scope вырос — создаётся новая задача.

**Почему не меняем:** SP = оценка сложности **до** работы, не учёт фактических трудозатрат. Изменение после старта делает velocity бессмысленной метрикой.
