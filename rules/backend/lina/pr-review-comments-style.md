# Inline-комменты в PR-ревью — короткие и человечные

**Когда применять:** при оставлении inline-комментариев в Pull Request коллег.

**Правило:**

- **Очень коротко.** 1–2 мысли максимум, без воды и многоступенчатой аргументации.
- **Без эмодзи, markdown-заголовков, выделений жирным.** Просто текст.
- **Без формальных ярлыков** типа «🔴 Блокер:», «Задача 3 не выполнена», «По спеке…». Критичность считывается из контекста.
- **Прямые вопросы:** «зачем нам это?», «а разве не `<=`?», «может лучше …?».
- **Мягкая подача через личное:** «мне кажется», «нас спасёт», «мне понадобится» — вместо «нужно сделать X».
- **Кросс-ссылки между комментами:** «то же с none и 0», «если поправим логику…» — не дублировать объяснения, опираться на соседние комменты.
- **Кодовые предложения** в блоке ```` ```python ```` — если уместно показать вариант.
- **Без ссылок на PRD/спеку** — рассуждать от инженерной логики.
- **Без выкладок:** что не так, чем грозит, что сделать. Без таблиц, цепочек «было/стало» и перечня файлов и
  строк, где это проверялось. Подробный разбор пункта — в диалоге до коммента, в коммент идёт выжимка.
- **Если развёрнуто** — через примеры («например, мне понадобится…»), не через bullet-points.
- **Ответ на замечание к своему PR** — с маленькой буквы, без точки; на простое замечание одно слово: «перенесла», «убрала». Что именно сделано, автор видит в диффе.

**Примеры:**

```
зачем нам тут отдельный класс? обычной функции хватает
```

```
а разве не <=? с равенством граничный кейс попадает в обе ветки
```

```

```

```python
# может проще так?
qs.filter(deleted_at__isnull=True, status='active')
```

**Почему:** коллеги читают много комментов в день. Длинные, формальные, эмодзи-перегруженные тексты вытесняются. Короткое в этом стиле читается и принимается лучше. Один тезис в одном месте, пояснение в другом — комменты работают вместе, не повторяя друг друга.
