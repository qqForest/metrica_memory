# Раскладка тестов по файлам

**Когда применять:** куда положить новые тесты или кейсы доступа.

**Правило:**

- Сначала смотреть базовую ветку и раскладку соседних PR — это уклад, а не вкус.
- **Ветки от `development`:** файл на action (`test_schedule_retrieve.py`,
  `test_settings_establishments_partial_update.py`). Кейсы доступа — в конец файла того action, который
  они проверяют.
- **Эпик прав (`development-permissions`):** один файл на эндпоинт, кейсы доступа (`test_list_401`,
  `test_list_403` и т. п.) — разделом `# ── доступ ──` в конце. Кейсы основной логики под суперюзером не
  трогать. Перед правкой структуры открыть `gh pr diff` ближайшего PR эпика и повторить его раскладку.
- Если файл уже есть (хоть с суффиксом `_access`) — дописывать в него, новый модуль не заводить.
- **Новый параметр в нескольких эндпоинтах** — кейсом в файле каждого ресурса, не файлом на параметр.
  Ассертом в существующий тест, если его ассерты не завязаны на точный состав данных; иначе отдельный
  тест в том же файле.
- Кейсы, отличающиеся только пользователем (суперюзер в другом тенанте), сливать в основной тест того же
  статуса.

**Почему:** `tests/` нарезаны по ресурсу и action; файл на параметр ломает порядок и не экономит время —
фикстуры поднимаются на каждый тест заново.
