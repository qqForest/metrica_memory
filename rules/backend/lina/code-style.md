# Стиль кода — мелкие правила

## Аргументы при вызове — позиционно

Аргументы нашего кода передавать позиционно, чтобы вызов помещался в строку. По имени — только
необязательный параметр, перед которым пропущен другой необязательный. Kwarg-only `*` не форсить,
существующие вызовы с kwargs попутно не переписывать.

```python
raise ShiftException(ShiftException.ROLE_NOT_IN_SCHEDULE, detail, field_name='profile_id')  # status_code пропущен
```

Почему: так пишут в проекте (75% вызовов), Руслан против растянутых именованными аргументами вызовов (MCA-764).

## return одной строкой

ФИО, тернарники, словари на несколько ключей считать в переменных выше, возвращать короткое выражение.
Многострочный `return {...}` и тернарник с переносом не писать — вместо тернарника обычный `if`.

Почему: в пятистрочном `return` теряется точка выхода.

## Литерал вместо одноразовой константы

Константу заводить, только если значение используется в 2+ местах или это публичный контракт. Ради длины
строки не заводить ни константу, ни атрибут класса, ни кортеж с `*args` — переносить строку
(`audit_logger.bulk_log(LogTypeChoices.ABSENCE, ...)`). Словарь-конфигурацию в стороне от кода не заводить:
две-три особенности — прямо в методы. Не спорит с «return одной строкой»: там переменная ради `return`, здесь
запрет на косвенность ради вызова.

Почему: при одном использовании константа не страхует от разъезда, а добавляет строку и импорт (решение
Руслана, MCA-1005).

## Классы выше функций

В модуле сначала классы, функции — под ними. «Спусти под класс» — переставить ниже в файле, не делать методом.
Функция с несколькими вызовами остаётся функцией модуля; с одним вызовом и правилом с ветвлением —
`@staticmethod` в классе, где её зовут.

Почему: в MCA-898 проверку спрятали в класс, для MCA-906 её пришлось доставать.

## Без реэкспортов в `__init__.py`

Импортировать из модуля, где класс живёт (`from shifts.models.schedule_target import ScheduleTarget`); в
`__init__.py` и `__all__` не добавлять. Соседние реэкспорты не образец, попутно не чистить.

Почему: два пути импорта одного имени; Руслан уберёт реэкспорты отдельно (MCA-1361).

## Без лишних проверок

Одно условие в нескольких местах — свести к одной проверке. Ветку под состояние, отсечённое выше по стеку
(права, скоуп, валидация сериализатора, глобальная пагинация), не писать: поломка инварианта пусть
вылезет 500-й. Пример: `user.role.in_schedule`, а не `... if user.role_id else True` — без роли скоуп `none`.

## Type hints — везде, без строковых аннотаций

Аннотации на всех аргументах и возврате, реальными типами. При циклическом импорте —
`from __future__ import annotations` или `if TYPE_CHECKING:`, не `'User'` в кавычках.

## Суффикс `_services.py`

Модули в `<app>/services/` — с суффиксом `_services.py`, имя по содержимому (`commit_services.py`).
Исключение — `services.py` для общих утилит приложения.

## Связанные записи — в одной транзакции

Несколько связанных записей (`create` + `.set()` на M2M, родитель + дочерние) — в одном `transaction.atomic()`
в сервисе, см. [[service-layer]] (PR #465).

## Код под снос не трогать

Если правка сделала код мёртвым, а на его снос уже есть задача — код и форму ответа оставить, удалить только
тесты, которые падают на исчезнувшем поведении. Перед попутной чисткой проверить, нет ли такой задачи.
