# Чего в тестах не делать

**Когда применять:** при написании тестов и при правке тестовой инфраструктуры.

**Правило:**

- Эффект изменения (деактивация, смена пароля) проверять одним сквозным сценарием через реальный API под этим
  пользователем: `GET` 200 → `PATCH is_active=false` → `GET` 401. Не набором точечных тестов. Источник: ревью PR #457.
- На удалённое тестов не писать: ни 404/405 на выпиленные маршруты, ни `assert 'field' not in response`.
- Эффект пока не виден через API — тест не пишем, ждём задачу с эндпоинтом. Загрузчики вида `load_logs()` в
  `tests/fixtures/` не заводить — там только фабрики `create_*`.
- Пакеты только ради тестов (`fakeredis` и т. п.) не тянуть — инфру мокать (`MagicMock`, как redis в
  `BaseTestCase.login`).
- Известные безобидные варнинги не глушить `filterwarnings` в `pytest.ini` — объяснять причину.

**Почему:** сценарий через API доказывает поведение, которое видит пользователь. Отсутствие маршрута гарантирует
роутер, такой тест ничего не защищает и ломается при перестройке URL. Лишний пакет — лишняя поддержка, фильтр
варнингов рискует спрятать важное.
