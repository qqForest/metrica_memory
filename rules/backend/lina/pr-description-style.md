# PR description — выжимка, не эссе

**Когда применять:** при заполнении description к Pull Request (включая автогенерацию через `/get_desc`).

**Правило:** описание помещается в один экран без скролла.

**Целевой объём:**

| Секция | Размер |
|---|---|
| **Что** | 1–3 строки |
| **Почему** | 2–4 буллета, по одной строке каждый |
| **Тесты** | 1–2 строки, упомянуть **файлы**, не перечислять кейсы |

**Не включать в описание:**

- Альтернативы и trade-off'ы («был вариант А, выбрали Б, потому что…»).
- Обсуждения с командой («согласовано с …», «после ревью с Русланом …»).
- Контекст из переписок и обоснования через ссылки на родительские задачи.
- Перечисление «N тестов в файле X» — достаточно «тесты на happy path и null-кейсы».
- «но», «однако», «вместо этого», «на самом деле» — каждая фраза в «Почему» одна короткая мысль.

**Шаблон:**

```markdown
## Что
Добавил bulk-lock TimeClock'ов через POST /timeclocks/lock-bulk/.

## Почему
- Менеджер закрывает зарплатный период одним действием, не по одному.
- Lock = иммутабельность: нельзя изменить approve_status, payroll_minutes.
- Аудит lock_by/lock_at для финансового разбора.

## Тесты
tests/shifts/test_timeclock_lock_bulk.py — access, idempotency, partial scope.
```

**Почему:** PR-описания читают коллеги в перерывах. Полстраницы текста — повод нажать «Approve» не глядя. Выжимка «что и почему» в одной картинке проверяема глазами за 5 секунд.
