# Naming и комментарии — компактно, без задачи в коде

**Когда применять:** при написании любого кода — модели, сериализаторы, сервисы, миграции.

**Правило:**

## 1. Полные имена переменных, без сокращений

```python
# Хорошо
start_time, end_time, start_datetime, end_datetime
effective_start_time
time_slot

# Плохо
start_t, end_t, start_dt, end_dt
eff_start
ts
```

Тривиальность кейса не оправдывает сокращение.

## 2. Docstring и help_text — одна строка по сути

```python
# Хорошо
"""Денормализованные datetime начала и окончания смены."""
help_text='Денормализованные datetime начала смены.'

# Плохо
"""
= combine(date, effective_start_time, current_tz).
Заполняется при создании WorkShift и обновляется
при изменении start_time/end_time.
Используется в Celery-задачах для фильтрации.
"""
```

Никаких подробностей реализации, никаких «когда заполняется / где используется», никаких ссылок на задачи.

## 3. Номер задачи (MCA-XXX) — никогда в коде

```python
# Запрещено
# MCA-246: денормализованные datetime
# Generated for MCA-178
class Meta:
    fields = ['id', 'start_datetime']  # MCA-246
```

**Единственное исключение:** устоявшийся паттерн `# TODO: удалить после MCA-XXX` — он указывает на **будущую** работу, а не на текущую.

## 4. Если комментарий нужен — он должен объяснять смысл, а не повторять имя

```python
# Плохо — дублирует имя функции
def compute_shift_datetimes(...):
    # Вычисляет datetime начала и конца смены
    ...

# Плохо — повторяет очевидное
result = compute_shift_datetimes(shift_date, start_time, end_time)
# Вычисляем datetime смены
```

Если функция называется `compute_shift_datetimes` — отдельный комментарий над вызовом не нужен.

**Почему:** контекст задачи живёт в трекере и PR, не в коде. Подробности реализации читаются из самой реализации. Имя — это контракт; комментарий — для того, что имя не может выразить.
