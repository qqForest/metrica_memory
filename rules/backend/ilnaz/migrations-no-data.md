# Миграции = архитектура, данные = из дампа

**Когда применять:** при написании или ревью миграций.

**Правило:** миграции содержат **только структурные операции** (`AddField`/`AlterField`/`RemoveField`/`Add/RemoveIndex`/`Add/RemoveConstraint`/`CreateModel`/`DeleteModel`/`RenameField`).

- **Никаких `RunPython`** с переносом или генерацией данных.
- **Никаких `RunSQL`** с DML (`INSERT`/`UPDATE`/`DELETE`).
- Seed / LEGACY-данные накатываются дампом БД, не миграциями.

**Исключение:** `RunSQL` для чисто структурных операций, которые ORM не поддерживает (например, partial-индекс с PostgreSQL-специфичным синтаксисом) — допустим, но с осторожностью и с `reverse_sql`.

**Почему:** позиция команды (Руслан, PR #334): «миграции собирают архитектуру БД, потом дамп накатывается». Data-миграции засоряют историю, не воспроизводят на свежей БД полезного state (LEGACY mapping `kitchen → Кухня` бесполезен, если в свежей БД нет старых строк), и часто становятся необратимыми. Если PR содержит data-миграцию — пересмотреть подход: создаются ли эти данные через fixture/seed-команду или они в дампе. Связано: [[no-handwritten-migrations]], [[never-drop-db]].
