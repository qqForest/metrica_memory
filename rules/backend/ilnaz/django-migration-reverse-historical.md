# Reverse миграций работает через historical state

**Когда применять:** при оценке безопасности перемещения операций между миграциями, или при чтении замечания «эта миграция уже на проде, нельзя редактировать».

**Правило:** Django при `migrate <app> <prev>` **не смотрит** на текущее состояние БД или модели — он восстанавливает state по цепочке миграций до точки отката и применяет обратные операции по этому state. Поэтому:

- `RemoveConstraint(name='X')` при reverse найдёт **полное определение** констрейнта (`UniqueConstraint(condition=..., fields=..., name=...)`) в исторических миграциях выше по цепочке и сделает корректный `AddConstraint`.
- Перемещение `RemoveConstraint` / `RemoveField` / `RemoveIndex` между миграциями **безопасно** с точки зрения rollback-semantics, если полное определение находится в истории.

**НЕ безопасно:** удалить `RunPython` / `RunSQL` без замены — `reverse_code`/`reverse_sql` теряются, обратная миграция становится no-op (структурная часть отрабатывает, но данные не восстанавливаются).

**Почему:** на ревью PR #334 я ошибочно поднял блокер «правка уже-применённой 0038 ломает rollback», потому что мысленно сравнивал с текущим состоянием боевой БД. Руслан показал, что Django reverse работает через **исторические** state-модели — итог симметричный. Это исправляет ментальный model: не любое редактирование уже-боевой миграции опасно. Связано: [[migrations-no-data]], [[sync-migrations-after-edit]].
