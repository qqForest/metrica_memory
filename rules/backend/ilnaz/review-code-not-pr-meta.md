# При ревью — только код и задача, без мета

**Когда применять:** при проведении code review PR.

**Правило:** смотреть **только** на код и на то, решает ли он задачу. **Не** выносить как замечания:

- Лейблы PR (`feature` vs `bugfix`, `hotfix` vs `tech debt` и т.п.).
- Галочки в чек-листе самопроверки автора (например, «Миграции корректны и обратимы» при отсутствии миграций).
- Имя ветки, заголовок PR, форматирование описания PR.
- Микро-косметика, не меняющая поведение (лишняя пустая строка между импортами, точка в конце docstring).
- «Скоп PR смешан» / «вынести в отдельный PR», если коммиты делают то, что заявлено в описании.

**Допустимо как замечания:**

- Любая логика, корректность, контракт API, обработка edge cases.
- Тесты: покрытие, корректность ассертов, порядок ([[test-ordering]]), фикстуры.
- Импорты, циклические зависимости, действительные технические проблемы в коде.
- Скрытые регрессии, дыры в валидации, потенциальные баги.

**Почему:** мета-замечания (лейблы, чек-лист, оформление) — шум, который снижает сигнал ревью и тратит время автора на правки без эффекта. Ревьюер ценен тем, что находит **в коде** то, что автор не увидел. Автор сам разберётся с лейблами и галками. Зафиксировано прямой репликой пользователя на ревью PR #337: «забей на чек-листы, забей как выглядит пиар, нам код важен. и выполняет ли он задачу».
