# ТЗ важнее паттернов

**Когда применять:** при расхождении требований задачи (Tracker MCA-XX) и проектных паттернов.

**Правило:** делать строго по ТЗ. **Не** добавлять поля/действия «для единообразия» с каноническим паттерном (аудит-лог, computed-поля и т.п.).

- **Глаголы из ТЗ читать буквально.** «Изменение» = PATCH, не DELETE. «Удаление» = DELETE, не soft-archive. «Создание» = POST, не «POST + автогенерация связанных».
- **Computed-поля не добавлять сверх ТЗ.** Derived-значения вычисляются на фронте из существующих полей; если нет — это отдельная задача после уточнения.
- Уточнения «не расширить ли до нашего паттерна?» больше не задавать — отвечать по умолчанию «нет».

**Почему:** паттерны — референс по стилю (наследование от `BaseModel`, расположение в сервисах, абсолютные импорты), **не** основание расширять scope. Карпати: «минимализм первым», «хирургические правки». На MCA-320 я расширил запрет «изменения» на DELETE и добавил `source`-поле «для удобства фронта» — оба раза получил откат. Связано: [[no-dead-guards]] (тот же дух — не копировать паттерны вслепую), [[basemodel-default]] (исключение: `BaseModel` — инфраструктура, не накручивание полей).
